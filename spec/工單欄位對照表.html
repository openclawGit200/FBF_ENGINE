FBF ENGINE · 工單合約

一張工單，一個單號

整張單就是 W-00X 一個號。它自己不填內容，内容是九關裡各角色輪流填的欄位： 每關交件 → 引擎守衛按欄位擋 → 過關推進，缺欄位就退回交給件的角色補（不推進、但不停）。 下表逐關列出：誰填、填什麼、引擎擋什麼。

00backlog 待派工→ 01design 解法→ 02acceptance_design 定驗收→ 03build 施工→ 04verify 驗收→ 05adjudicate 結案裁決→ 06closed 結案
退回支線（adjudicate 判 rework）：rework_design 重做設計 → rework_build 重做施工 → 回 verify（輪次 +1，重工上限 2 次）。

工單本體 works 引擎

引擎開單、引擎推進。人只確認需求、裁決卡住處。角色從不直接寫这张單，只透過交件填欄位。

欄位意義
work_id
TEXT		 整張單的唯一單號（如 W-001）。所有關卡、交件、缺口、回執都挂在这个号上。
version
INT		 樂觀鎖。每次推進 +1；角色重交件要帶 expected_version，對不上就重新讀單再交，避免兩棒撞車。
rework_count
INT		 重工次數。達上限（2）後不能再 rework，改走 review 檢討或等人裁決。
state
9 態		 現在跑到哪關。引擎依 state 決定下一棒派給誰、交件要哪些欄位。
awaiting_human
0/1		 卡住等人。人可用 CLI 裁決：放行重試 / 改寫 / 作廢。

01 解法設計 design THINKER 填

對問題出至少兩案，由 THINKER 在同一棒直接產出（不分派 SUBAGENT、不帶 context id）。兩案不得實質相同：成本與修改範圍不能都一樣。三句話講不完的問題應該拆單，不是硬寫。

欄位填法與守衛
solutions
list ≥ 2 案		 每案六欄：approach · cost · change_scope · effort · risk · verifiable_by；選填 reuses。案號＝解法清單的順序（1 起算），不另設欄位。兩案不得實質相同（成本與修改範圍不能都一樣）。 solutions.count / solution.too_similar / solution.field_missing
design_note
text		 設計說明：做了什麼、為什麼這樣做。design_note.missing
交出去候選方案＋選擇依據 → 下一關 PLANNER 選案、定驗收。

02 定驗收方式 acceptance_design PLANNER 填

整張單唯一產生「題目」（checks 答案卷）的一關。每條題目必須掛到一條「人已確認」的需求；門檻和必驗項目只能加不能降。

欄位填法與守衛
selection
object		 solution_id（選哪案＝案號，1 起算，如 "1"）· reason · rejected_because（為什麼不選其他案）。 selection.missing / selection.unknown_solution
checks
list ≥ 1 條		 每條題目八欄：id（題號）· requirement_id · method（怎麼查）· scope · threshold（什麼算過）· evidence（要附什麼證據）· required（必驗/參考）· execution_kind（test 跑程式 / review 目視）。 checks.missing / check.field_missing / check.requirement_unknown / requirement.unconfirmed / check.threshold_lowered / check.required_downgraded / check.result_deleted
交出去答案卷（checks 表）→ 施工照做、驗收照它逐條作答。

03 施工 build WORKER 填

照答案卷把活做完。產物只報指紋（路徑/大小/SHA-256），引擎自己重算對現檔，不採信自報數字；路徑必須落在專案根內。

欄位填法與守衛
outputs
list ≥ 1 項		 每項：path（相對專案根最佳；根內絕對路徑引擎自動轉）· size · sha256。 outputs.missing / evidence.missing / evidence.hash_mismatch
done · unfinished
list		 做完了什麼、沒做完什麼；空清單也要交。unfinished.invalid
selfcheck
text		 交件前照答案卷自檢一遍的結論。selfcheck.missing
cases_ran
number		 實際跑的案例數，不得灌水；純文件/目視的工單自報 review 類。cases_ran.zero
交出去產物指紋＋自檢結論 → 驗收者拿它逐條核對。

04 驗收 verify THINKER 填

拿答案卷逐條作答：結果的 id 就是题目的 id，不自造編號。驗收者不能是本單施工的那個 session（自做自驗會被擋）。總判引擎算，不聽角色自報：所有必驗全 PASS＝pass，任一必驗 FAIL＝fail，其餘＝partial。

欄位填法與守衛
results
list ≥ 1 項		 每項：id（＝ checks 表的題號）· status（PASS／FAIL／PARTIAL／NOT_RUN）· reason · evidence。 result.missing（某條 check 沒結果）/ result.status_invalid / result.evidence_missing / verify.self_conflict
cases_ran
number		 實測案例數。cases_ran.zero
交出去逐條答案＋總判（引擎算）→ PLANNER 裁決 close 或 rework。

05 結案裁決 adjudicate PLANNER 填

三選一，只交需要的那組欄位（其餘填空字串）：

欄位填法與守衛
action
close / rework / review		 方向。action.missing / action.invalid
close_reason（close 時） 結案理由。引擎另查總判：verdict 不是 pass 不能 close。verdict.partial / verdict.fail
rework_reason · rework_type（rework 時） 退回原因（下一棒會引用）＋類型（施工錯／驗收錯／解法錯）。重工達上限 2 次後走不下去。rework.limit_reached
diagnosis · remedy（review 時） 重工達上限後的重新檢討：病因（work／acceptance／solution／scope／resource）＋處方（halt／revise，revise 上限 2）。 review.diagnosis_invalid / review.remedy_invalid / revision.limit_reached
交出去close → closed；rework → rework_design（支線）。

支線 重做 rework_design → rework_build

被 rework 退回後走這邊。改法設計（THINKER）＋重做施工（WORKER），完事回 04 驗收，輪次 +1。

欄位填法與守衛
rework_plan
text · THINKER		 針對退回原因設計的改法，要引用那個原因。action.missing
outputs / done / unfinished / selfcheck / cases_ran
WORKER		 與 03 施工同一套欄位、同一套守衛。

06 結案 closed 引擎推進

無欄位。引擎推進；專案層的人類收工（project close）要通過雙向追溯：需求 ↔ 工單 ↔ 證據全掛得上。

公共：交接八欄 handoff 每個角色填

每關交件都附一份交接檔——下一棒接棒前要讀，缺任一欄整單被退。八欄固定：

欄位寫什麼
ROLE這一棒的角色
OPEN WORK還沒做完的事
SUBAGENTS RUNNING還在跑的 subagent
RULES AND NUMBERS IN FORCE目前有效的門檻／範圍／資源上限（可能已變，別用舊值）
RECIPES可重用的做法
DECISIONS AND WHY已做的決定與理由
LESSONS踩過的坑
SPEND花掉的資源

缺口代碼：handoff.missing

答案卷 ↔ 答案 checks → results

02 關產生題目，04 關逐條作答。答案的 id 跟著題目的 id，不自造。

題目（checks，PLANNER 在 02 填）

checks 表 · 每行一條

id: C-01
requirement_id: R-001
method: 跑 e2e 檢查表
threshold: 四項全 PASS
execution_kind: test
required: 1

答案（results，THINKER 在 04 填）

results 表 · id 抄題號

id: C-01            ← 抄自題目
status: PASS
reason: 四項皆達
evidence: 指紋重算一致

總判（引擎算，不聽角色自報）：所有 required=1 全 PASS → pass；任一必驗 FAIL → fail；其餘 → partial。05 關 PLANNER 拿總判裁決。

目前卡住處 W-001 / W-002 / W-003 @ verify

已知卡點

答案卷是空的。這三張單從沒走過 02（checks 表 0 條），04 卻要「每條 check 交一個結果」—— 題目不存在，驗收者交任何 id 都被判 result.missing，重交幾次結果一樣。

單據本身沒寫錯，錯在上游漏了 02 這棒＋被退的訊息只說「某條 check 沒有結果」、沒說是「答案卷空」。待決修法： （a）三張單補走 02 由 PLANNER 建 checks；（b）守衛兜底——checks 為空時驗收者依工單內容自列驗收項， 並把「id 照 checks 表填；清單為空就自列」直接寫進 04 單據欄位說明。

被退時怎麼回執 rejects & receipts

退件不是停流程：把缺項退回交給件的角色補，補齊重交；同一關連續被退 3 次或回執核對 3 次到期 → 標 awaiting_human 等人裁決。

缺口代碼每筆退件帶穩定代碼＋人看得懂的說明（缺哪欄、怎麼補），同一問題永遠同一個代碼。
回執錨點交件時角色帶 task_id＋message_id；引擎到平台上核對「提示詞真的進了、回合真的跑了」才算 verified。
重試上限退回 3 次、回執到期 3 次、重工 2 次、修訂 2 次——達限一律轉人，不無限重錘。
欄位與缺口代碼皆摘自 fbf_engine/workflow.py 的守衛定義（提示詞與守衛共用同一份欄位清單）。生成於 2026-11-23。
