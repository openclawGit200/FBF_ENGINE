# 2026-11-20 — OpenCode 2.2.5 的平台契約（實測）

> 這是**證據與觀察**，不是決策。決策寫在 `docs/decisions.md`（附則五／附則六）。

## 怎麼取得的

不是靠猜，也不是靠文件。兩條路交叉驗證：

1. **上游原始碼**：GitHub `anomalyco/opencode` tag `v2.2.5`
   （`packages/schema/src/session-message.ts`、`packages/protocol/src/groups/message.ts`、
   `packages/protocol/src/groups/session.ts`、`packages/cli/src/commands/handlers/api.ts`）。
2. **真實資料**：Mac 上 `~/.local/share/opencode/opencode.db` 的 `session_message` 資料表
   （127 MB，含 11,362 則 assistant 訊息）＋ `~/.local/share/opencode/log/opencode.log`
   （CLI 版本 `2.2.5`）。

**注意**：網路掛載上直接讀 SQLite 會 `disk I/O error`（讀 WAL 時）→
必須先把 `.db`／`.db-wal`／`.db-shm` 三檔複製到本機再唯讀（`mode=ro&immutable=1`）。

## 端點契約

| 端點 | 回應 |
|---|---|
| `GET /api/session/active` | `{"data": {"ses_x": {"type": "running"}}}` — **以 session id 為鍵的物件** |
| `GET /api/session/{id}` | `{"data": {...session info...}}` |
| `GET /api/session/{id}/message` | `{"data": [...], "cursor": {"previous":..., "next":...}}` |
| `GET /api/experimental/session/{id}/export` | `{"data": {"info": {...}, "messages": [...]}}` |

`/api/session/{id}/message` 的查詢參數：`limit`（1–200，**預設 50**）、`order`（asc/desc）、
`cursor`（不透明游標，**不可與 order 同用**）、`type`（依訊息型別過濾）。

**預設只回 50 筆的尾端視窗** → 長 session 的派工訊息會被截掉，
必須照 `cursor.next` 往前翻頁，否則回執核對必然失敗。

`opencode api GET <path>` 會把 path 原樣交給 `fetch(new URL(path, endpoint.url))`
→ **查詢字串可用** ✓。不帶 `--server` 時 CLI 會自行找到本機 server（連認證一起處理）✓。

## 訊息形狀（扁平，不是 `{info, parts}`）

```jsonc
// 使用者訊息
{"id": "msg_…", "type": "user",
 "text": "【FBF ENGINE 派工】task_id: T-000001 …",
 "time": {"created": 1795159510000}}

// assistant 訊息
{"id": "msg_…", "type": "assistant", "agent": "build",
 "model": {"id": "group/never-stuck", "providerID": "magpie", "variant": "default"},
 "content": [{"type": "tool", "id": "call_…", "name": "execute",
              "state": {"status": "completed",
                        "input": {"code": "const r = await tools[\"fbf-engine\"].fbflow_report_work({…})"},
                        "content": [{"type": "text", "text": "{\"ok\":true,…,\"submission_id\":\"S-000001\"}"}]}}],
 "finish": "tool-calls",
 "time": {"created": 1795159510050, "streamed": 1795159510200, "completed": 1795159510300}}
```

型別值：`user`／`assistant`／`system`／`synthetic`／`compaction`／`idle`／
`agent-switched`／`model-switched`／`location-switched`／`skill`／`shell`。

`finish`（FinishReason）：`stop`／`length`／`tool-calls`／`content-filter`／`error`／`unknown`。

## 三個反直覺的實測結果

### 一、`time.completed` 不是「已完成」的證據

**帶 tool call 的中間步驟訊息也帶 `time.completed`** →
拿它推論完成，會把「還在跑」誤判成「已完成」。完成只看平台明講的 `finish`。

### 二、`completed` 比 MCP 交件**晚**不到一秒

同一工單的交件訊息：`completed` 比 submission 的 `created_at` 晚 0.1–1.0 秒
（平台在工具收尾之後才標 `completed`）。
→ 「回執必須早於提交」會誤殺正確回執；必須留容差（實作取 5 秒）。

### 三、agent 透過 `execute` 工具呼叫 MCP 工具

不是直接呼叫 `fbflow_report_work` 工具，而是跑一段 JavaScript：

```js
const report1 = await tools["fbf-engine"].fbflow_report_work({
  task_id: "T-000001", work_id: "W-001", expected_version: 2, stage: "design", payload: {…} });
```

→ 交件參數在**程式碼文字**裡，不在結構化的 input 欄位。

## 重試的樣子

同一工單交三次，前兩次是 **SyntaxError**（JavaScript 寫錯，工具根本沒跑），
第三次才真的產生 submission。工具回應裡有 `"submission_id"` → 那是「交件落地」的證據 ✓。

→ 回執要挑「工具回應有 submission_id」且**時間最接近提交**的那一則，
不是第一則、也不是最後一則。

## 真實資料上的驗收

拿 Mac 上真實的 14 筆提交 ＋ 真實訊息跑 `receipts.verify_opencode`：
**14/14 核對通過**，且每一筆對到**自己**那一則訊息（不是 14 筆共用同一則）。
